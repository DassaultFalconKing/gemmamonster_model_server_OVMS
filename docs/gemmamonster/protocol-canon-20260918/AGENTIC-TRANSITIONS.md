# Gemma4 agentic transition acceptance matrix — 2026-09-18

Status: **CANONICAL ACCEPTANCE CONTRACT**

Purpose: ensure OVMS preserves Gemma4's actual agentic behavior instead of making the model appear less capable by dropping or misrouting legal reasoning/content/tool transitions.

This document is intentionally stricter than a collection of isolated parser unit tests.

A real agent loop is a sequence of semantic phases:

```
reasoning
content
tool call
tool result
reasoning
content
tool call
...
final answer
```

The runtime must preserve the model's structural intent at every boundary.

---

# 1. Core invariant

For every generated byte/token there must be exactly one semantic owner:

```
reasoning bytes   -> reasoning_content
answer/prose      -> content
tool envelope     -> tool_calls
control markers   -> routing only, never user-visible payload
```

No valid structural tool call may disappear because the previous phase was reasoning or content.

No ordinary promise/prose may be promoted into an executable tool call merely because it mentions a tool.

This distinction is fundamental:

`"I will call read_file now."`

is not a tool call.

`<|tool_call>call:read_file{...}<tool_call|>`

is.

The parser must preserve the difference perfectly.

---

# 2. State-machine expectation

Conceptual phases:

```
UNKNOWN
CONTENT
REASONING
TOOL_CALLS_PROCESSING_TOOL
TOOL_CALLS_WAITING_FOR_TOOL
```

Required legal transitions for Gemma4 agentic use:

```
UNKNOWN -> REASONING
UNKNOWN -> CONTENT
UNKNOWN -> TOOL

REASONING -> CONTENT
REASONING -> TOOL
REASONING -> STOP

CONTENT -> TOOL
CONTENT -> STOP

TOOL -> TOOL
TOOL -> CONTENT
TOOL -> STOP
```

Across requests / tool-result turns:

```
TOOL_RESULT -> REASONING
TOOL_RESULT -> CONTENT
TOOL_RESULT -> TOOL
```

The exact internal enum names may evolve. The behavioral transition set must not.

---

# 3. A-series — single-generation structural transitions

## A01 — promise/prose -> real tool call

Input shape:

```
I need the repository contents.
I will call read_file now.
<|tool_call>call:read_file{...}<tool_call|>
```

Expected:

- promise/prose remains content unless it was emitted inside reasoning;
- exactly one real tool call is emitted;
- tool syntax does not appear in content;
- no duplicate tool delta;
- tool name/arguments are exact.

Purpose: prove that ordinary language immediately before a real call does not swallow the call.

## A02 — open reasoning -> real tool call, no explicit reasoning closer

Input:

```
<|channel>thought
I need to inspect the file.
I will use read_file.
<|tool_call>call:read_file{...}<tool_call|>
```

No `<channel|>` before the tool opener.

Expected:

```
reasoning_content:
  "I need to inspect the file.\nI will use read_file.\n"

content:
  ""

tool_calls:
  exactly one read_file
```

This is the currently confirmed lost C5 contract.

## A03 — explicit reasoning close -> real tool call

Input:

```
<|channel>thought
Need the file.
<channel|>
<|tool_call>call:read_file{...}<tool_call|>
```

Expected:

- same semantic result as A02;
- explicit close must continue to work after implicit-handoff repair.

## A04 — reasoning -> answer/prose -> real tool call

Input:

```
<|channel>thought
I should explain one thing first.
<channel|>
The repository may contain generated artifacts.
I will inspect the actual file.
<|tool_call>call:read_file{...}<tool_call|>
```

Expected:

- thought only in `reasoning_content`;
- explanatory answer only in `content`;
- later structural call still becomes `tool_calls`;
- no phase remains stuck in CONTENT.

This pins the “thought -> answer -> real tool call” transition.

## A05 — reasoning -> answer -> reasoning -> tool

If the current Gemma4 protocol/runtime permits reopening reasoning inside one assistant generation, test:

```
thought -> content -> thought -> tool
```

Expected:

- each reasoning block is routed as reasoning;
- content remains content;
- final call is executable;
- phase state resets correctly between segments.

If the protocol forbids reopening reasoning inside one assistant generation, record this case as protocol-invalid rather than silently deleting it from the matrix.

## A06 — content promise without structural call

Input:

`I will call read_file now.`

then STOP.

Expected:

- zero tool calls;
- content preserved;
- parser does not manufacture a call.

This is the negative pair for A01.

## A07 — reasoning promise without structural call

Input:

```
<|channel>thought
I should call read_file.
<channel|>
```

then STOP.

Expected:

- zero tool calls;
- reasoning preserved;
- no synthetic execution.

Promise detection may be useful as diagnostics, never as execution semantics.

# 4. B-series — fragmentation / streaming invariance

Every important transition above must be invariant to chunk boundaries.

At minimum run each applicable payload with:

1. whole payload in one chunk;
2. one token per chunk;
3. splits around every structural boundary;
4. split inside `<|tool_call>`;
5. split immediately before/after tool name;
6. split inside arguments;
7. split inside `<tool_call|>`;
8. STOP immediately after closer;
9. multiple structural elements coalesced into one decode flush.

Required invariant:

```
semantic output(full payload)
==
semantic output(any legal partition)
```

No bytes duplicated, lost, or reassigned to a different semantic channel.

# 5. C-series — multi-call transitions in one generation

## C01 — reasoning -> tool -> tool

Expected:

- reasoning correct;
- two tool calls;
- indices stable and ordered;
- second call not absorbed into first.

## C02 — reasoning -> tool -> content

Expected:

- tool A committed exactly once;
- trailing content preserved;
- tool syntax absent from content.

## C03 — content -> tool -> content -> tool

Input shape:

```
I'll inspect A.
tool A
A suggests B is relevant.
tool B
```

Expected:

- two content segments retained in order;
- two tool calls retained in order;
- no parser phase lock after the first tool.

This directly pins “answer -> tool call”.

## C04 — reasoning -> content -> tool -> content -> tool

Expected semantic order:

```
reasoning[0]
content[0]
tool[0]
content[1]
tool[1]
```

If the final API exposes accumulated strings rather than ordered semantic events, inspect streaming deltas to prove transition order.

# 6. D-series — real multi-turn agent loop

These tests run across actual tool execution and tool-result turns.

## D01 — think -> tool -> think -> final answer

```
user
  ->
assistant reasoning
  ->
tool call A
  ->
tool result A
  ->
assistant reasoning
  ->
final answer
```

Acceptance:

- tool A actually executes;
- result is fed back;
- second assistant turn can reason normally;
- final answer contains no stale tool envelope;
- no phantom second call.

## D02 — think -> tool -> think -> tool -> final answer

```
user
  ->
reasoning
  ->
tool A
  ->
result A
  ->
reasoning
  ->
tool B
  ->
result B
  ->
reasoning/content
  ->
final answer
```

This is the minimum serious agent-loop test.

A runtime that passes one tool call but loses the second is not agentically accepted.

## D03 — promise -> tool -> result -> answer -> tool

```
assistant:
  "I'll inspect A."
  tool A

tool result A

assistant:
  "A is useful, but I need B too."
  tool B
```

Acceptance:

- both promises remain prose;
- both real calls execute;
- second transition works after previous tool-result state;
- no parser state leaks across requests.

## D04 — tool result -> immediate tool

```
TOOL_RESULT -> TOOL B
```

must work without requiring filler reasoning or prose.

## D05 — tool result -> reasoning -> tool

```
TOOL_RESULT
  ->
open thought
  ->
tool B without explicit <channel|>
```

This combines multi-turn state with recovered P02.

## D06 — tool result -> reasoning -> answer only

Expected:

- no tool call;
- final response clean;
- parser does not remain stuck in tool-waiting state.

## D07 — tool -> reasoning -> answer -> tool

This explicitly covers the sequence requested for agentic acceptance:

```
tool A
  ->
tool result A
  ->
reasoning
  ->
visible answer/prose
  ->
tool B
```

Expected:

- tool A and B both execute;
- reasoning remains reasoning;
- visible answer remains content;
- tool B is not swallowed merely because content preceded it;
- no stale tool index or phase survives from A.

# 7. E-series — tool-choice policy matrix

Run representative A/D sequences under:

```
tool_choice=auto
tool_choice=required
tool_choice=<named tool>
```

## Auto

Valid outcomes include no tool call only when the model never emits a structural call.

Parser acceptance criterion:

- if raw opener exists, it must not disappear.

Generation diagnostic:

- promise + no raw opener is recorded separately.

## Required

At least one real structural call must occur.

Prose-only completion is failure.

## Named

At least one real call to the selected tool must occur.

Wrong-tool call is failure even if structurally valid.

# 8. F-series — raw-token / parsed-output correlation

For every live agentic test capture:

| Field | Required |
|---|---|
| request/turn ID | yes |
| prompt state | yes |
| raw token IDs | yes |
| decoded specials-visible output | yes |
| position of `<|tool_call>` or ABSENT | yes |
| position of `<channel|>` or ABSENT | yes |
| streaming reasoning deltas | yes |
| streaming content deltas | yes |
| streaming tool deltas | yes |
| final `reasoning_content` | yes |
| final `content` | yes |
| final `tool_calls` | yes |
| finish reason | yes |

Ownership classifier:

```
raw tool opener exists
+ tool_calls missing
    => runtime/parser failure

raw tool opener absent
+ auto
    => generation-side candidate

raw tool opener absent
+ required/named
    => hard generation failure
```

# 9. G-series — negative safety / non-fabrication

## G01 — tool syntax mentioned as documentation

Reasoning/content contains quoted tool syntax but not a legal structural opener in parser context.

Expected: no execution.

## G02 — non-Gemma reasoning parser

Qwen/Hermes or another parser emits tool-looking text inside reasoning.

Expected: no Gemma4 implicit phase transition.

## G03 — unknown tool

Legal-looking envelope names a tool absent from registry.

Expected: no executable tool call.

## G04 — malformed/truncated envelope

Expected:

- no executable tool call;
- later valid envelope can still recover if protocol permits.

Reliability work must not become “execute anything vaguely tool-shaped”.

# 10. H-series — acceptance metrics

For deterministic parser tests:

```
100% expected semantic outputs
0 marker leaks
0 duplicate calls
0 fabricated calls
0 lost valid calls
```

For live generation tests, report separately:

```
raw structural-call rate
parsed-call rate conditioned on raw structural opener
promise-without-opener rate
hard-choice violation rate
malformed-call rate
```

Do not collapse these into one “tool success rate”.

The most important runtime correctness metric is:

```
P(parsed valid call | raw valid structural call) = 1.0
```

for covered valid protocol forms.

If this is below 1.0, the harness is making the model artificially less capable.

---

# 11. Required implementation-test layers

The final recovery must have all four layers:

### Layer 1 — leaf parser

Focused reasoning/tool parser units.

### Layer 2 — OutputParser

Direct phase-transition tests, including split boundaries.

### Layer 3 — OVMSTextStreamer

Real tokenization/decode-mode tests with special tokens and streaming partitions.

### Layer 4 — live agent harness

Actual requests, actual tool results, actual second/third turns.

Passing Layer 1 is not evidence for Layer 4.

---

# 12. Forward-port rule

This matrix is a mandatory C6 and future-forward-port gate.

A refit is incomplete if it preserves individual parser classes but drops a legal transition between them.

The runtime must preserve the model's intelligence, not merely compile its components.
